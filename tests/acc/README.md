# تست‌های زندهٔ هستهٔ حسابداری کاربان

این مجموعه، رفتار **واقعی دیتابیس** را با کاربران واقعی احراز هویت‌شده (دقیقاً مثل خودِ اپ) می‌سنجد — نه Mock و نه Static Analysis.

## اجرا

```bash
npm run test:acc
```

## پیش‌نیاز

* دسترسی شبکه به Supabase پروژه (همان کلید anon که در `src/lib/supabase.ts` است)
* **دو کاربر آزمایشی** که هرکدام بتوانند یک کسب‌وکار آزمایشی (trial) بسازند
* برای اجرای کامل (بخش‌های RPC و تریگرها): ابتدا مایگریشن
  `supabase/migrations/20260920120000_acc_core_hardening.sql`
  را در SQL Editor اجرا کنید

## کاربران آزمایشی — سه راه

1. **متغیر محیطی (پیشنهادی برای اجراهای مکرر — بدون مصرف سهمیه ایمیل):**

```bash
ACC_TEST_USER_1=a@x.com ACC_TEST_PASS_1=... \
ACC_TEST_USER_2=b@x.com ACC_TEST_PASS_2=... \
npm run test:acc
```

2. **ثبت‌نام خودکار:** اسکریپت خودش دو کاربر می‌سازد — به سهمیهٔ ایمیل Supabase
   (حدود ۲ ایمیل در ساعت در پلن رایگان) محدود است. اگر «email rate limit exceeded»
   دیدید، یک ساعت بعد دوباره اجرا کنید یا از روش ۱ استفاده کنید.

3. **کاربران از پیش ساخته در پنل:** در Supabase Dashboard → Authentication دو کاربر
   بسازید (Email confirm را دستی true کنید) و با روش ۱ به اسکریپت بدهید.
   کاربران نباید دسترسی حسابداری فعال داشته باشند؛ اسکریپت خودش با RPC رسمی
   `acc_start_trial` کسب‌وکار می‌سازد.

## سناریوها (هم‌نام با بخش‌های درخواست حسابرسی)

| فایل | پوشش |
|---|---|
| `accounting.journal.concurrent.spec` | ۲۰ درج هم‌زمان — شمارهٔ یکتا، سند تراز، بدون ردیف خالی |
| `accounting.journal.atomicity.spec` | رد غیرتراز/منفی/خالی + تزریق خطا و Rollback کامل |
| `accounting.rls.business-isolation.spec` | جداسازی کامل دو کسب‌وکار (CRUD دوسویه) |
| `accounting.permissions.spec` | viewer ممنوعِ نوشتن؛ accountant با مجوز محدود در سطح DB |
| `accounting.invoice-void.spec` | صدور/ابطال اتمیک + سند آینه‌ای + موجودی + قفل‌های بعد از ابطال |
| `accounting.bank-reconciliation.concurrent.spec` | دو خط مشابه هم‌زمان → اتصال صحیح، بدون دوبل |
| `accounting.fiscal-year.spec` | بستن → اختتامیه → افتتاحیه + ممنوعیت ثبت در دورهٔ بسته و بستن مجدد |
| `accounting.trial-balance.spec` | تراز آزمایشی با سندهای شناخته‌شده + حذف ابطالی‌ها |
| `accounting.ledger-integrity.spec` | اسکن کل دفتر: سند ناتراز/یتیم صفر |
| `accounting.numeric-rounding.spec` | اعداد مرزی، مالیات، تخفیف، باقی‌مانده |
| `accounting.e2e.flow.spec` | سناریوی کامل کسب‌وکار خدماتی و سازگاری همهٔ مانده‌ها |
| `accounting.deletion.spec` | قوانین حذف برای همهٔ موجودیت‌های حساس |
| `accounting.reports.spec` | فیلتر تاریخ/کسب‌وکار/ابطال در گزارش‌ها و سازگاری با دفتر |

## وضعیت‌های خروجی

* **PASS** — واقعاً اجرا و تأیید شد
* **FAIL** — اجرا شد و نتیجه اشتباه بود
* **EXPECTED-FAIL** — رفتار فعلی پیش از مایگریشن ضعیف است؛ بعد از اجرای مایگریشن PASS می‌شود
* **SKIP** — پیش‌نیاز (معمولاً مایگریشن) اجرا نشده

نتیجهٔ هر اجرا در `tests/acc/out/results.json` ذخیره می‌شود.

## پاکسازی

در پایان هر اجرا، همهٔ کسب‌وکارهای آزمایشی به‌صورت آبشاری حذف می‌شوند
(تریگرهای قفل اجازهٔ حذف آبشاری کل کسب‌وکار را می‌دهند ولی حذف تکی سند قطعی را ممنوع می‌کنند).
